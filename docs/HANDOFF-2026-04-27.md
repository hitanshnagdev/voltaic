## The data flow as it stands

```
upload spec
  └─ ingest → classify → spec-classified
      ├─ parse-spec → spec_paragraphs (+identity)
      │   └─ spec-paragraphs-written
      │       ├─ embed-spec-paragraphs → embeddings on spec_paragraphs
      │       └─ parse-spec-checklist → spec_checklist_items
      │           └─ for each prior assignment to this spec:
      │               fire submittal/extract-against-checklist-ready

upload submittal
  └─ ingest → classify → submittal-classified
      ├─ parse-submittal → submittal_fields (legacy panelboard schema)
      │   └─ equipment/aic-ready, /sccr-ready, /enclosure-ready (3 rules fire)
      └─ suggest-assignment → auto-suggested submittal_spec_assignment row
          (user confirms / overrides in /docs AssignModal)

PM clicks Assign in /docs
  └─ POST /api/assignments → submittal_spec_assignments row inserted
      └─ fire submittal/extract-against-checklist-ready
          └─ extract-against-checklist (the runner that has the bug)
              ├─ load checklist for (spec, csi_section)  ← 176 items if csi=null
              ├─ load submittal PDF from R2
              ├─ Sonnet vision call with checklist as context
              └─ persist submittal_checklist_responses

PM opens /compare?submittal=<id>
  └─ buildCompareDataForSubmittal joins assignments × checklist × responses
  └─ verdict computed inline by computeVerdict() per row
```

## Known bugs / gotchas (read these before touching anything)

### 1. Whole-spec assignment extraction silently fails — `csi_section: null`

**Repro:** Assign a submittal to a spec without picking a specific CSI section. Wait. `submittal_checklist_responses` stays empty.

**Cause:** `extract-against-checklist.ts` loads ALL checklist items for the spec when `csi_section` is null. The demo spec has 176 items. The Sonnet vision call gets a 31K input + needs 44K output. Either truncates mid-response (caught by extractJson if fence is partial) OR errors. No `llm_calls` row appears because the function may be erroring before the API call.

**Fix (next session, ~1 hour):**
- Batch checklist by `csi_section` when assignment is whole-spec
- Add Anthropic prompt caching with `cache_control: { type: "ephemeral" }` on the document block — PDF is identical across batches
- Cost analysis: naive batching = $1.68/submittal, with caching = $0.80/submittal, with semantic pre-filter = $0.28/submittal

**Operational workaround (now):** Have user pick a specific CSI section in the AssignModal dropdown. Limits checklist to ~15 items per section.

### 2. Hardcoded panelboard shim is dormant but still imported

`lib/rag/compare/attributes.ts` is no longer consumed by `/compare` (PR #45 replaced it). But `lib/db/compare.ts` previously imported types from there — verify no stale imports remain. The legacy AIC/SCCR/Enclosure rule runners (`analyze-project.ts`, `analyze-sccr.ts`, `analyze-enclosure.ts`) still use `tag_normalized` matching and are independent of the spec-driven path. They produce findings on `/today` but their data flow is parallel to the new compare flow.

### 3. Inngest function registration race

When a new Inngest function is added in `app/api/inngest/route.ts`, Inngest Cloud has to discover it via the `/api/inngest` endpoint. After deploy, this usually happens within a minute. Events fired DURING this window may be dropped silently. Mitigation: re-fire the event manually if a recently-deployed function didn't pick up its first event.

### 4. Vercel deploy URLs vs canonical alias

Production alias is `voltaic-ten.vercel.app`. Per-deploy URLs like `voltaic-jpsiibonn-...vercel.app` are immutable snapshots. If user signs in on a per-deploy URL, their Clerk session cookie is bound to that domain — they stay on the stale build. **Bookmark `voltaic-ten.vercel.app` only.**

### 5. Migrations don't auto-apply on Vercel deploy

After any `drizzle/post/*.sql` change, run `DATABASE_URL='<prod>' npm run db:migrate` manually. As of this handoff, all migrations through `005_submittal_checklist_responses.sql` are applied.

### 6. Voyage 3 RPM free tier

Embed cache from #38 prevents repeat calls but first-time queries still hit Voyage. If you see Voyage 429s, either (a) wait a minute, (b) check the embed cache table, (c) suggest adding payment to dashboard.voyageai.com.

### 7. Hard API budget constraint

User has $10 on Anthropic. **Do not call the Claude API for verification runs without explicit permission.** Always quote cost first. Reference table:

## What the user wants built next: agent conversation surface

**User direct quote:** *"separate the agent conversation with the compare tab, the agent conversation should be a free flowing conversation that takes place in an interface similar to dataagrid or any agentic ai platform, where users should be able to ask any questions about the attached spec or submittal, we already have the spec and submittal clauses in our vector db, we just need to allow the user to be able to have a agentic conversation about anything about the spec and submittals"*

### Why this is right architecturally

`/compare` is structured verification (the table view). An agent chat is exploratory ("does this spec say anything about labeling?"). Different workflows. The original CLAUDE.md design squashed them together; DECISIONS.md U14 superseded that with the structured table; this handoff promotes chat to its own first-class surface.

### What's already in place

- **Schema:** `chat_sessions` + `chat_messages` tables exist in `lib/db/schema.ts`. Never wired to a UI.
- **Retrieval:** `lib/rag/retrieve/hybrid.ts` works — BM25 + vector + RRF, scoped by project, supports filters.
- **Streaming:** Anthropic streaming + citations API are both wired in `lib/llm.ts`.
- **Embeddings:** `spec_paragraphs.embedding` populated. `spec_checklist_items` and `submittal_checklist_responses` are NOT yet embedded — small text, ~5 min to add if needed.

### What needs building

| Layer | Scope |
|---|---|
| **Route** | `/ask` (avoid `/chat` collision with future stuff). Server component shell. |
| **UI** | Client component: scroll history above, sticky composer below. Streaming response render. Citation chips inline (`[26 24 16 §2.05/B p.4]`) that scroll to / link to source. ChatGPT-style. |
| **API** | New `/api/ask` POST endpoint. Streams via `ReadableStream`. Each request: load session history, run retrieval on the latest user message, build context, stream Sonnet, persist user + assistant messages to `chat_messages`. |
| **Sessions** | URL: `/ask?session=<id>`. Sidebar lists recent sessions with title (auto-generated from first user message). |
| **Cost meter** | Per-session running cost from `llm_calls` joined to session. Visible in the chat UI. **Important** given the $10 budget. |
| **Prompt caching** | Anthropic ephemeral cache on the system prompt + retrieved doc context across turns in a session. Drops per-turn cost from ~$0.025 to ~$0.005 after the first turn. |

### Implementation order (suggested)

1. Schema sanity check (`chat_sessions` + `chat_messages` already exist — verify they match what we want)
2. Build `/api/ask` POST with retrieval + streaming + persistence (no UI yet, test with curl)
3. Build the chat UI client component with streaming render
4. Wire session sidebar
5. Add cost meter
6. Add prompt caching
7. **Get user approval before any Claude API verification calls.** UI testing without real chat = mock the streaming response.

### What to NOT build

- Tool use for "show me page X" — defer until v1 chat works
- Multi-doc selection in the composer — start with project-scoped retrieval
- File upload from the chat — uploads happen on `/docs`
- Saved prompts library — defer to v2 (per CLAUDE.md, was originally a Compare feature)

## Recent technical decisions worth remembering

### Manual assignment > implicit tag matching

The pivot in this session: instead of auto-extracting `tag_normalized` from submittals and joining to specs by CSI section, the PM explicitly assigns each submittal to a spec section. Auto-suggest pre-fills the picker. Many-to-many table. This eliminates the silent-zero failure mode that broke ~half of real-world submittals.

### Spec-driven extraction > hardcoded schema

The previous compare page asked the model to find ~10 panelboard fields regardless of what the spec actually required. The new flow: spec parser produces a typed `ChecklistItem` per requirement; submittal vision answers each item specifically. Eliminates the "guess what fields to ask for" problem.

### Citation guard via overlap

Per-field `evidence_quote` + Anthropic citations API + 50% token-overlap threshold catches hallucinated values without being too strict. Live in `parse-submittal` (passive) and `extract-against-checklist` (active dropping).

### Caching architecture

- `hash_cache` table memoizes deterministic operations on content bytes (parse-spec-paragraph, parse-submittal-vision, embed)
- Voyage embed cache prevents 429s and repeat-cost
- Anthropic prompt cache for the next layer (PDF + checklist contexts) — NOT YET WIRED, biggest near-term cost saving
