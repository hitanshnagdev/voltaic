## Priority 2 — End-to-end test with a fresh spec + submittal pair

**The current demo project has** `spec-26-24-16-panelboards.pdf` + `submittal-mdp-2-schneider.pdf`. Both are AI-synthesized fixtures designed to produce a clean hot-AIC finding. They've been ingested, parsed, assigned, and extracted across multiple sessions.

**The user wants to verify the pipeline works on something fresh.** The right test is to pick a real-ish public-domain pair and walk it through end-to-end. Real PDFs surface bugs that synthesized fixtures don't.

**Suggested sources for the test pair:**
- **GSA Design Excellence:** https://www.gsa.gov/real-estate/design-and-construction/design-excellence
- **State university capital projects:** UC, UT, CSU systems all post full bid sets
- **USACE UFGS:** Unified Facilities Guide Specifications
- **Bid posting boards:** DemandStar, BidNet, BidSync

**For the simplest first test, look for:** any Division 26 spec section (panelboards / switchboards / transformers / motor control) + a vendor cut sheet that matches that section (Square D, Eaton, Siemens, ABB).

**The end-to-end flow to verify:**

```
1. /docs → drag spec PDF → wait
   ✓ doc_type detected as "spec"
   ✓ status reaches "ready"
   ✓ spec_paragraphs populated (CSI structure parsed)
   ✓ spec_checklist_items populated (typed checklist extracted)

2. /docs → drag submittal PDF → wait
   ✓ doc_type detected as "submittal"
   ✓ status reaches "ready"
   ✓ submittal_fields populated (legacy panelboard schema — fine to be empty for non-panelboard equipment)
   ✓ suggest-assignment fires → submittal_spec_assignments row appears with source='auto-suggested'

3. /docs → click "Assign" on the submittal → confirm or override the suggestion
   ✓ assignment persists with source='manual' if overridden
   ✓ POST /api/assignments fires submittal/extract-against-checklist-ready
   ✓ extract-against-checklist runs (now batched per #50, no longer 176-item explosion)
   ✓ submittal_checklist_responses populated

4. /compare?submittal=<id> → see the Airtable-style table
   ✓ rows render for each checklist item
   ✓ verdicts are correct per the comparator (numeric ≥, enum =/in, boolean =, etc.)
   ✓ MISSING rows for items the submittal is silent on
   ✓ category filter works
   ✓ status pills work

5. /ask → type "what does the spec require for this equipment?"
   ✓ retrieval surfaces the relevant spec_paragraphs
   ✓ streaming response cites them inline
   ✓ chat history persists in chat_sessions / chat_messages
```

**Bugs to specifically watch for (these failed silently in prior testing):**
- Auto-suggest returning a stale spec assignment (race when submittal upload happens before spec is parsed)
- Equipment-tag extraction returning null when the cut sheet has no project tag (legacy parse-submittal path) — the new spec-driven path bypasses this but the legacy AIC/SCCR/Enclosure rules still depend on it
- The 176-item explosion (FIXED in #50 but verify on a real spec with many sections)
- Inngest event drop window after deploy if function registrations changed recently
- Voyage 3 RPM rate limit if many documents uploaded in parallel
- Per-deploy URL drift (always test on `voltaic-ten.vercel.app`, not preview URLs)

**Operational steps after upload:** if you add a new spec and the project's old assignments need re-extraction with the new checklist, the parse-spec-checklist runner emits the re-extract event automatically. But if you re-upload an existing spec by dragging the same file, the content_sha256 cache hits and nothing re-runs (this is correct behavior).

**Migration check:** if you've added schema changes locally, run `DATABASE_URL='<prod>' npm run db:migrate` after merging. Prior migrations through `005_submittal_checklist_responses.sql` are applied; verify the next session hasn't queued a new one.

## Priority 3 — Surface confidence scores in the UI

**Confidence is in the DB everywhere. It's invisible in the UI.**

| Where it lives | Type | What 0.0..1.0 means |
|---|---|---|
| `spec_checklist_items.confidence` | numeric(4,3) | How sure the parser was about extracting this requirement (0.95 = clear, 0.5 = ambiguous) |
| `submittal_checklist_responses.confidence` | numeric(4,3) | How sure the model was about the value found (0.95 = clear quote backing, 0.3 = synthetic "not found" row) |
| `submittal_spec_assignments.confidence` | numeric(4,3) | Auto-suggest confidence (manual = null, auto-suggested = 0.5..1.0) |
| `findings.confidence` | numeric (legacy AIC/SCCR/Enclosure path) | Already surfaced as a chip on `/today` |

**Where to surface it:**

| Surface | What to show |
|---|---|
| `/docs` row for a submittal | Assignment confidence next to "Assigned · 1" pill (small "92%" or "auto-suggested · high") |
| `/docs` row for a spec | Average checklist-item extraction confidence ("47 items · avg 0.91 confidence") |
| `/compare` per-row | Confidence chip next to the verdict ("OK · 95%" / "FLAG · 87%"). The Airtable redesign makes this easy — add a column. |
| `/compare` summary | Average row confidence ("12/15 evaluated · avg confidence 0.88") |
| AssignModal | When showing an auto-suggested assignment: pill with confidence + rationale ("Suggested 26 24 16 — confidence 0.92 · 'Cover lists Square D NQOD panelboard'") |
| `/ask` citations | Each cited paragraph could carry its checklist-item-extraction confidence — useful when the chat is reasoning over auto-extracted data |

**Visual design suggestion (low-friction):**
- 0.85+ → no chip (high confidence is the default, don't add visual noise for everything)
- 0.6–0.85 → small grey chip ("0.72")
- <0.6 → small amber chip with warning glyph ("⚠ 0.45")

The point is to make low-confidence verdicts visually distinct so PMs know where to spot-check. High confidence should NOT be loudly celebrated — that creates banner-blindness.

**Implementation order:**
1. Pure formatter helper: `confidenceChip(value: number) → ReactNode | null`. Lives in `lib/ui/confidence.tsx` (new).
2. Add to `/compare` first — easiest win, most visible, single column to add.
3. Add to `/docs` per-row — coupled with the Priority 1 revamp; combine the work.
4. Add to AssignModal for auto-suggested assignments.
5. Add to `/ask` citations last — only matters once chat usage warrants it.

**Calibration warning:** the absolute confidence numbers are not yet calibrated against ground truth. They reflect the model's self-reported confidence with some boundary smoothing in our validators. Until the eval harness lands (operational item below), these are *relative* trust indicators, not absolute probabilities. Visual scale should reflect that uncertainty — chips, not big numbers.

## Recent technical decisions worth remembering

- **Manual assignment > implicit tag matching.** PM explicitly assigns each submittal to a spec. Auto-suggest pre-fills. Many-to-many table.
- **Spec-driven extraction > hardcoded schema.** Spec parser produces typed `ChecklistItem` per requirement; submittal vision answers each item specifically.
- **Citation guard via overlap.** Per-field `evidence_quote` + Anthropic citations API + 50% token-overlap threshold catches hallucinated values.
- **Batched extraction + Anthropic prompt caching (#50).** PDF cached across batches via `cache_control: { type: "ephemeral" }`; checklist split by CSI section. ~5x cheaper for whole-spec assignments.
- **System Map dropped.** Confirmed at the architectural level, removed from sidebar in #51. Reflects CLAUDE.md "Honest risks" — drawings dependency is too deep without a drawing parser.
- **Citations graceful fallback (#56).** Some Sonnet responses return `citations: []` even when the response is valid — handle this defensively rather than throwing.
- **Compare page redesigned to Airtable style (#52, #53, #54).** Status pills + category filter + 5-pill toolbar. New visual baseline for tabular surfaces in the product.
